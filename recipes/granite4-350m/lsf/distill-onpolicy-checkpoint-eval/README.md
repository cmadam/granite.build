# distill-onpolicy-checkpoint-eval — on-policy GOLD from c2000, every rung fully evaluated

**Written, not yet run.** 2,500 steps of on-policy GOLD distillation (granite-4.0-350m ←
granite-4.1-3b), starting from **c2000**, the off-policy step-2,000 checkpoint. A checkpoint
every 500 steps, each exported and fanned out to **all 27 evaluations** of
[`full-eval`](../full-eval/build.yaml) as it is written. The output is one file:
`combined.csv`, a benchmark × checkpoint table.

It is [`distill-checkpoint-eval`](../distill-checkpoint-eval/README.md)'s graph with
[`distill-onpolicy-v2`](../distill-onpolicy-v2/README.md)'s vLLM server and teardown spliced
in. Read those two READMEs for the mechanisms; this one covers what is new.

## Why here, why c2000

c2000 is export-2000 of build `1e2e969e` (`distill-350m-ckpt-eval-20260929`, rung
`ckpt_2000`). The checkpoint-ladder report found 73% of the off-policy epoch's capability
lift already present at step 1,000. The index was flat after that: steps 2,000 → 8,150 bought
GSM-Symbolic and Minerva and gave back ~2 SALAD points. Against the 30B-teacher reference
run, c2000 beats that run's final checkpoint on 11 of 13 axes. So the off-policy objective
has banked what it can by step 2,000. The variable left to try is where the sequences come
from.

At `LMBDA 0.25`, one sequence in four is generated by the student and scored by the
teacher; three are still corpus text. Everything else is c2000's run, and the tests assert
it: the pair, the pinned corpus, the objective (`beta 0.5`, no CE anchor), effective batch
96, the LR schedule, `MAX_LENGTH`, the eval suite.

## The data sampler, and the step change it needed

c2000 trained on this pinned corpus at 2 × 8 GPUs × 2 × 3. HF Trainer seeded its sampler
from the default `seed` 42, because the `distill-gold` step never rendered a seed. A fresh
run from c2000 at the same corpus, geometry and seed draws **the same permutation**. Its
steps 1–2,000 would be c2000's own 192,000 rows again, in the same order. Three quarters of
every batch would be a second pass over text the model has already fitted, and an on-policy
gain could not be told apart from a second-look gain.

`distill-gold` now renders `data_seed`, which reseeds the sampler and nothing else (`seed`
stays 42). It is a stock `TrainingArguments` field, so it is not gated on a patched trainer.
At `GOLD_DATA_SEED 43`, this run's 240,000 rows overlap c2000's at the base rate, 192,000 /
782,388 ≈ 24.5% (~59,000 rows), instead of 80%. `-1` omits the key and restores the replay.

**Check it on the first launch.** The rendered trainer config is printed into the workload
log between `--- rendered gold config` and `--- end gold config ---`, and it should carry
`data_seed: 43`. Nothing upstream of the trainer can prove the sampler honours it.

## Two things that are unmitigated, and where to look

- **Immediate-EOS collapse.** `MIN_COMPLETION_LENGTH` is 0 because neither half of a
  generation floor exists at the step's trainer pin; see
  [`distill-onpolicy-v2`](../distill-onpolicy-v2/README.md). An empty completion is a
  rollout the teacher scores as if it were one. `gen-smoke` binds every export, so it runs
  only at the end. **The early read is rung 500**: its `eval-transfer-500` entropy, and its
  full-eval row (IFEval and the generation-heavy suites drop first on empty completions).
  Both arrive mid-run, while there is still a run to cancel.
- **A crashed trainer strands the server.** `teardown` is gated on
  `train-gold.checkpoint`, which a crash never emits. `VLLM_MAX_LIFETIME_SECONDS` is the
  backstop, now **24 h** rather than v2's 5 h. The clock starts when the server comes up,
  before the 16-GPU trainer allocation clears the queue. The run itself has never been
  measured: at 2–3× off-policy's 5.9 s/step it would take ~8–12 h. The price is up to
  ~48 GPU-h stranded on a crash. If the trainer dies, down the cluster by hand:
  `gb build log <id> --runner --all | grep -i "SkyPilot job.*on gb-"`, then `sky down`.

## Reading combined.csv

`<SAGE_RESULTS_DIR>/distill-350m-onpolicy-c2000/combined.csv`, columns `ckpt_500` …
`ckpt_2500`. **These are on-policy steps**: `ckpt_500` is c2000 + 500. The comparators are
c2000's own column (`distill-350m-ckpt-eval-20260929-ckpt_2000`) and the off-policy run's
later rungs (`ckpt_3000`, `ckpt_4000`), which saw the same number of additional steps
off-policy. Note that those rungs did *not* restart the LR warmup or the optimizer, and this
run does: it starts from the export, with fresh Adam moments, a 125-step warmup and a
2,500-step cosine.

`EXPERIMENT` is distinct from the off-policy run's on purpose. Both write into the shared
sage tree keyed by `<EXPERIMENT>-ckpt_<N>`, and a shared name would overwrite c2000's
results with this run's `ckpt_2000`. The other traps when a row reads 0.000 are the
off-policy README's: BFCL tool-format failures, and a dropped `rope_theta`. c2000's
`config.json` carries the top-level `rope_theta` 10,000,000, checked 2026-10-02.

## Launch

`bcb-server` must be up first:

```bash
gb build start -f recipes/granite4-350m/lsf/bcb-server/build.yaml --space <space>

gb build start -f recipes/granite4-350m/lsf/distill-onpolicy-checkpoint-eval/build.yaml \
  --space <space> --param OE_EVAL_BCB_API_URL=http://<host>:7860/evaluate/
```

**Shake it down first.** On-policy plumbing (server, URL binding, weight sync, teardown) and
the mid-run watcher have each run, but never in one build:

```bash
gb build start -f recipes/granite4-350m/lsf/distill-onpolicy-checkpoint-eval/build.yaml \
  --space <space> \
  --param RUN_NAME=distill-350m-onpolicy-c2000-shakedown \
  --param EXPERIMENT=distill-350m-onpolicy-c2000-shakedown \
  --param GOLD_MAX_STEPS=4 --param GOLD_SAVE_STEPS=2 --param CKPT_LADDER=2,4 \
  --param EVAL_CATEGORIES=bfcl --param VLLM_MAX_LIFETIME_SECONDS=7200
```

Read four things off the shakedown:
- the server's request log is non-empty;
- the rendered config carries `data_seed`;
- `checkpoint_2` and `checkpoint_4` are emitted mid-run;
- `teardown` downs the server cluster.

The shakedown's per-step wall clock is also the first on-policy timing on this pair.
Multiply it by 2,500 and check that against `VLLM_MAX_LIFETIME_SECONDS` before the real
launch.

`RUN_NAME` **must** differ per launch (the `b5f030cd` artifact-collision mode; see the
off-policy README).

| `gen-smoke` | 1 H100 | 1 | minutes, at the end |
| sage evals + `eval-bfcl-ck<N>` | 1 H100 each | 135 | ~4 GPU-h per rung |
